# REGRESSION TEMPLATE — Гибкие напоминания

Регламент проведения регрессионного тестирования.

**Когда использовать:**
- После каждой крупной волны разработки
- Перед публикацией релиза
- После обновления зависимостей или изменения архитектуры
- Раз в 1–2 недели для профилактики

---

## Как проводить регрессию

### Подготовка

1. Скачать свежий APK из GitHub Actions (или собрать локально).
2. Установить на тестовое устройство (основной телефон).
3. Подготовить APK предыдущей версии — для проверки обновления.
4. Убедиться, что заряд устройства > 50%.
5. Отключить агрессивные оптимизации батареи для приложения (Xiaomi/Huawei/Samsung).
6. Открыть `CHECKLIST_IMPLEMENTED.md` — будем по нему идти.

### Проведение

1. Пройти по всем пунктам `CHECKLIST_IMPLEMENTED.md`.
2. По ходу — фиксировать результаты (✅ / ❌ / ⚠️).
3. При обнаружении багов — создавать Issue в GitHub, прикреплять метки severity/priority.
4. Продолжать прогон, даже если найден критичный баг — важно увидеть всю картину.
5. По завершении — заполнить отчёт.

### После завершения

1. Все найденные баги — заведены как Issues.
2. Критичные баги — назначены в milestone ближайшего релиза.
3. Отчёт сохранён в `docs/regression-reports/` (по шаблону `_TEMPLATE.md`).
4. Если всё зелёное — можно готовить релиз.
5. Если есть Critical баги — релиз блокируется до их исправления.

## Правила классификации

### Severity (насколько сильно сломан функционал)

| Уровень | Описание | Пример |
|---|---|---|
| 🔴 Critical | Приложение падает, теряет данные, блокирует работу | Краш при запуске, потеря напоминаний после обновления |
| 🟠 High | Нарушена ключевая функция, но приложение работает | Уведомления не приходят вовремя |
| 🟡 Medium | Функция работает с дефектами, есть обходной путь | Валидация не срабатывает, но можно сохранить |
| 🟢 Low | Косметика, не влияет на работу | Кривое выравнивание текста |

### Priority (насколько срочно фиксить)

| Уровень | Когда фиксить |
|---|---|
| P1 | Немедленно, релиз блокируется |
| P2 | В ближайшем релизе |
| P3 | Можно отложить до следующей волны |
| P4 | Когда-нибудь, если будет время |

**Соотношения по умолчанию:**
- Critical → P1
- High → P2
- Medium → P3
- Low → P4

Но бывают исключения: например, критичный визуальный баг на главном экране = High/P2, а косметика в редком диалоге = Low/P4.

---

## Критерии прохождения регрессии

Регрессия считается пройденной, если:

- ✅ Пройдено > 95% тест-кейсов
- ✅ Нет открытых Critical багов
- ✅ Нет открытых High багов (или они запланированы на следующий релиз с обоснованием)
- ✅ Medium и Low задокументированы
- ✅ Обновлён `CHECKLIST_IMPLEMENTED.md`
- ✅ Отчёт сохранён в `docs/regression-reports/`

## Частота регрессии

| Ситуация | Что проводить |
|---|---|
| После каждой волны разработки | Полная регрессия |
| Перед публикацией релиза | Полная + Test Run |
| Мелкий багфикс | Точечная проверка затронутых модулей |
| Регулярно | Smoke-тест раз в неделю |
| Обновление зависимостей | Фокус на затронутых модулях |

**Smoke-тест** (быстрая проверка, ~15 минут):
- Создание напоминания
- Срабатывание уведомления
- Отсрочка уведомления
- Выключение / включение
- Перезагрузка устройства
